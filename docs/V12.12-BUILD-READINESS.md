# V12.12 build readiness — October 11, 2026

The current source includes phrase selection, stem export, cancellable background jobs, live meters and full-song level checks. This pass validates the accumulated changes and repairs build scripts; it does not introduce another application version or produce a Windows installer.

## Verified locally

- **31 C++ test executables passed**, compiled from the current source with GCC and the available JUCE 9.0.2 core/events/audio-basics/audio-formats objects. This covers native dictation with a fake Vosk library, vocal tuning/effects/harmony, presets' supporting skin logic, song recording/editing/recovery, export, meters and level checks. These were direct compiler runs, not CMake/CTest execution.
- **52 Python unit tests passed** via `python -m unittest discover -s Tests -p 'test_*.py' -v`.
- Editor, processor and ProcessorTests.cpp passed JUCE-header syntax checking; this does not replace linking or running the processor test.
- Linux/macOS shell-script syntax passed `bash -n`.
- Detailed C++ and Python outputs are stored in [CPP results](validation/V12.12-CPP-RESULTS.json) and [Python results](validation/V12.12-PYTHON-RESULTS.txt).

The real speech-model smoke test was not run. The linked GUI/processor regression executable was not run. No native app window, plugin host, installer or AudioBox was exercised.

## Native build blocker

The first configuration attempt stopped because CMake was absent. A follow-up installed CMake 3.31.10 and pkgconf 2.5.1 locally under the ignored build directory, without changing the application source. Configuration then reached compilation of JUCE's `juceaide` build tool and failed on the missing FreeType development header `ft2build.h`. Audio/GUI development dependencies remain unavailable. The system package-manager attempt failed because the environment does not permit its user/group switching operations; no dependency-installation workaround was applied.

GCC and previously built non-GUI JUCE objects permit the checks above, but do not establish that a complete native build passes.

Windows and macOS validation require their own toolchains. The PowerShell build script was reviewed here but could not be executed because this environment is not Windows and has no PowerShell runtime. No GitHub workflow was triggered or pushed. The local workflow now includes the `v12.12-build-readiness` branch, explicitly enables tests and rejects empty test runs. Once a push is approved, that existing workflow is configured to build/test on Windows and macOS, run plugin/speech gates and create downloadable package artifacts. Success is not guaranteed: native or packaging failures must be addressed from the actual job logs. This preparation does not merge the branch or publish a GitHub release.

## Build-script fixes

- Windows packages now derive their version from `CMakeLists.txt`, instead of always being named V10.
- Windows checks for CTest and includes `BUILD-INFO.txt`, test logs and the existing documentation in its portable ZIP.
- Missing optional preview images do not abort packaging.
- Linux/macOS scripts work from their repository directory and correctly quote a JUCE path containing spaces.
- Linux/macOS build all configured targets, including tests; macOS includes its already configured AU target.
- All three scripts run CTest and treat an empty test suite as an error. A failed configure, build or test run stops the script.

## Windows: build, locate and launch the program

On your Windows computer, install Visual Studio 2022's **Desktop development with C++** workload, Windows SDK and CMake tools. Git/network access is needed for JUCE unless you supply an existing checkout. Use a Developer PowerShell terminal at the repository root.

For a first native application build without packaging the separate Audio Lab companion:

```powershell
.\scripts\build-windows.ps1 -BuildDirectory build-win-v12.12 -SkipAudioLab
```

With an existing JUCE checkout, add:

```powershell
-JucePath "C:\path to\JUCE"
```

The script configures, builds and runs the registered native tests. Only after those pass does it assemble a portable folder and ZIP. A successful run prints their exact paths.

Expected folder name:

```text
IDW-V12.12.0-Windows-<timestamp>
```

Open **Run-IDW.cmd** inside that folder. The actual executable is:

```text
Windows\Standalone\IDW Voice MIDI Studio.exe
```

The VST3 bundle is under `Windows\VST3`. This is a portable build, not an installer, and it does not install/replace plugins automatically. `-SkipAudioLab` omits the separate Audio Lab executable; it does not claim the full companion/model package is ready. Speech/model availability must be checked separately. Existing `START-HERE` files may describe earlier releases; use `BUILD-INFO.txt` and the current manual for this build.

If the script fails, keep the terminal output and the build directory. Native test details are under `build-win-v12.12\Testing\Temporary\LastTest.log`. Do not treat an older executable or a partially assembled release directory as a successful new build.
